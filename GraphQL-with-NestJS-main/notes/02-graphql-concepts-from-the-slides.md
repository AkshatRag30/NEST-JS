# 02. What GraphQL Actually Is, From the Lecture Slides

The `lectures` folder contains one slide deck, `GraphQL Explained.pdf`, from the same TechZeen course this repo's code is built around. It is very short, five slides total, and it stays purely conceptual, no NestJS syntax appears anywhere in it. This note walks through those five slides in plain language before any code, the same way you would want a concept explained to you before being handed a file full of decorators. [03-the-book-object-type-and-schema.md](03-the-book-object-type-and-schema.md) onward ties every idea here directly back to the real files in `src`.

## Slide one and two: what GraphQL is

The deck opens by defining GraphQL plainly: "GraphQL is a query language for APIs," developed by Facebook in 2012 and released publicly in 2015. A query language, in this sense, is not a general purpose programming language, it is a language specifically for describing what data you want back from a server, the same role SQL plays for a database, except GraphQL's job is describing a request to an API rather than a database table directly.

The deck's next point is the one that matters most for understanding why this technology exists at all: "It allows the client to request exactly the data it needs, nothing more or less." That single sentence is the entire philosophy behind every decorator you will see in `book.model.ts` and `book.resolver.ts`. In a REST API, the server decides, once and for all, what shape of data a given endpoint returns, every client that calls `GET /books` gets the exact same fields every time, whether it needs all of them or not. In GraphQL, the server instead exposes a menu of everything that is possible to ask for, and the client writes a query that picks exactly which fields it wants for that one request. Two different clients can hit the exact same GraphQL endpoint and get back two completely different shapes of data, one asking only for a book's title, another asking for its title, author, and description, without the server needing two different routes to support that.

The deck names this problem directly: "GraphQL solves problems of over fetching and under fetching in REST APIs." Over fetching means a REST response contains more fields than the client actually needed, wasted bandwidth and wasted parsing on the client's end. Under fetching means the opposite, a single REST endpoint does not return enough related data, forcing the client to make a second, or third, follow up request to a different endpoint to gather everything it needs for one screen. GraphQL's answer to both problems is the same single idea: let the client describe the exact shape of the response it wants, in the request itself.

Slide two closes with the detail that ties directly into how this project's `GraphQLModule.forRoot()` is configured: "Works on a single endpoint, not multiple like REST." A REST API is normally a whole family of URLs, `/books`, `/books/:id`, `/authors`, `/authors/:id`, each one its own route with its own fixed response shape. A GraphQL API, by contrast, exposes exactly one URL, in this project that is `/graphql` (the address `@nestjs/apollo` sets up automatically once `GraphQLModule.forRoot()` runs, as covered in [01-project-setup-and-graphql-module.md](01-project-setup-and-graphql-module.md)). Every single operation, whether it is fetching all books, fetching one book, or creating a new one, goes through that one same URL, as an HTTP POST carrying a GraphQL query or mutation as its payload. What changes between operations is not the URL, it is the text of the query itself.

## Slides three and four: why GraphQL over REST, with a concrete example

The third slide is just a section title, "Why Use GraphQL over REST?", and the fourth slide answers it with a worked example rather than more abstract bullet points. It restates the over fetching and under fetching problem, then makes it concrete: "Getting a user profile might return posts, friends, and settings, even if you just need the name." Picture a REST endpoint like `GET /users/:id` that was designed to support a full profile page, so it always returns the user's name alongside their entire list of posts, their full friends list, and their account settings. Now picture a completely different part of the same app that only needs to show a user's name next to a comment they left, nothing else. With that REST endpoint, there is no way to ask for less, the server sends back everything it always sends back, posts, friends, and settings included, even though only the name will ever be used. That wasted data is over fetching in a nutshell.

The slide's answer: "With GraphQL, you ask only for what you need. No extra data." Translating that into this project's own shape (this exact example is not literally in the code, since `Book` is a small object with no nested relations to over fetch from, but the principle is identical): a GraphQL client asking for a book's title only would write a query containing just `title`, and the server would respond with only that one field. A different client, on the same endpoint, could ask for `title`, `author`, and `description` all at once, and get back exactly that. [06-the-resolver-queries-and-mutations.md](06-the-resolver-queries-and-mutations.md) shows this happening for real with the `getAllBooks` and `getBook` operations. The slide's closing line, "GraphQL is faster, flexible, and efficient," is really just the payoff of that one idea, letting the client shape its own response tends to mean less data sent over the wire and fewer separate network round trips needed per screen.

## Slide five: the difference between GraphQL and REST

The final slide is only a title card, "Difference Between GraphQL and REST API," with no bullet points following it in this particular deck (the slide deck ends there). Even without its own bullet list, the difference has effectively already been laid out across the first four slides, and it is worth stating plainly as a summary before moving into code. A REST API is many endpoints, each with a server chosen, fixed response shape, and a client typically needs to piece together data from several requests to assemble what one screen actually needs. A GraphQL API is one endpoint, with a schema that lists every type of data and every operation available, and the client, not the server, decides the exact shape of each individual response by writing a query. The schema is the contract between the two sides, it tells a client everything it is allowed to ask for, without dictating exactly what any single response has to contain, and `schema.gql` in this repo, generated straight from the `@ObjectType()`/`@InputType()`/`@Resolver()` decorators covered in the notes that follow, is a literal, on disk copy of that contract for this specific project.

One more distinction worth naming here, since it appears constantly once you open the code: GraphQL splits its operations into two kinds, queries and mutations. A query reads data without changing anything on the server, `getAllBooks` and `getBook` in this project are both queries. A mutation changes data, creating, updating, or deleting something, `createBook`, `updateBook`, and `deleteBook` are all mutations here. The slides do not use this exact vocabulary, but it is standard GraphQL terminology that every file from `book.resolver.ts` onward depends on, and [06-the-resolver-queries-and-mutations.md](06-the-resolver-queries-and-mutations.md) walks through exactly how each one is written in this codebase.
