# Roadmap and Milestones

## Suggested pace

There is no fixed deadline attached to this project, but a rough pace is worth having so you can tell whether you are stuck on something worth being stuck on, or stuck on something you should ask for help with. Phase 1 typically takes a determined beginner a full weekend, since it involves setting up two databases and every cross cutting concern at once, and being slow here is completely normal and worth not rushing. Phases 2 through 6 are the heart of the project and each one reasonably takes another weekend or a handful of weekday evenings, since each one introduces at least one genuinely new idea rather than repeating the previous phase's pattern. Phase 7, the GraphQL layer, tends to go faster than the phases before it once your Prisma service layer already exists, since most of the work is a new API shape wrapping logic you already wrote. Phase 8 is short. Phase 9, real testing, is worth taking as seriously as any feature phase, it is not a wrap up chore. Phase 10 is optional and open ended, do it whenever the comparison feels useful rather than as a hard requirement.

## Milestones and what done looks like at each one

After phase 1, you should be able to start the app, see both database connections confirmed in the log, and confirm the app refuses to start at all with a missing environment variable, with nothing else built yet. After phase 2, you should be able to sign up, log in, and hit one protected route with a real token, and have that route genuinely reject a missing, expired, or tampered token. After phase 3, an instructor should be able to build a small real course catalog, and an anonymous client should be able to browse only the published parts of it. After phase 4, a student should be able to enroll, track progress, and leave a review, with the review correctly blocked if no enrollment exists. After phase 5, that same flow should only be reachable through a real order, with a transaction you have personally watched fail and roll back cleanly at least once. After phase 6, enrolling or reviewing should produce a real notification in a completely separate database, and you should be able to unplug MongoDB and watch the primary flow keep working anyway. After phase 7, the exact same course data should be fetchable through GraphQL, with a field level resolver you have proven only runs when actually requested. After phase 8, rapid repeated login attempts should visibly get rate limited while normal traffic does not. After phase 9, the full suite should pass from a clean checkout with fresh test databases, not just on your machine in whatever state it happens to be in.

## The one exercise worth doing after every single phase, not just at the end

Trace one real request through every layer it touches, out loud, in your own words, without opening the code while you do it, the exact thing note 18 (`18-request-lifecycle-recap.md`) and note 11 (`11-full-recap-and-file-map.md`) already modeled for you in two of the reference projects. After phase 5 specifically, trace a single `POST /orders` call all the way from the HTTP request, through the guard, into the transaction, through both the success and the failure branch, and back out as a response, and only move on to phase 6 once you can do that from memory.

## What to do when a phase reveals the earlier plan was wrong

Some phases in this plan will turn out to be slightly wrong once you actually start building, that is normal and expected, not a sign of a bad plan, a plan written before any code exists always has some of this. Phase 5's PRD already flags one example ahead of time, it explicitly changes how enrollment creation works from what phase 4 built. When you hit a moment like that yourself, write it down in a short running notes file of your own next to this planning folder, what changed, and why, the same honest habit the eight reference projects' own notes practiced when they found a real bug or gap instead of pretending the code was perfect.
