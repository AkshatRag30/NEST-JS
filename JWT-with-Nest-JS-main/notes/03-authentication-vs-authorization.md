# 03. Authentication vs Authorization

## Why the slides open with this distinction

The deck spends its first four slides, half the entire presentation, on nothing but this one distinction, before JWT is even mentioned. That ordering is deliberate and worth keeping: JWT is a mechanism, a way of carrying proof of who someone is and letting a server check that proof cheaply on every request, but authentication and authorization are the two separate problems that mechanism ends up being used to solve. Understanding the two ideas on their own terms first makes the login flow in the previous note make a lot more sense, since that flow is really "authentication, using a JWT as the proof."

## Authentication, as the slides define it

The slide titled "Authentication" defines it in three bullets: "Verifying who the user is." "Example: Logging into your Gmail using email & password." "It checks if you are a real & registered user." In plain terms, authentication is the question "are you who you claim to be." The Gmail example the slide picks is a good one because it is something almost everyone has done directly: you type in an email address and a password, and Gmail's servers check whether that combination matches an actual registered account. If it does, you have been authenticated, the system now has a reasonable basis for believing you are the specific person who owns that account, rather than a stranger.

Authentication is fundamentally about identity, and it typically happens once, at the start of a session, when you first log in. Everything that follows, every other request you make while using the app, relies on the system remembering the outcome of that one authentication check rather than asking you to enter your password again on every single click. This is exactly the gap a JWT is designed to fill, as the previous note covers: instead of the server remembering "this session is user 42" in some server side store, the proof of that earlier authentication travels with the client, inside the signed token, and gets verified again (not performed again from scratch) on each new request.

## Authorization, as the slides define it

The slide titled "Authorization" defines it just as directly: "Decides what the authenticated user is allowed to do." "Example: A normal Gmail user can't access Admin Panel." "It checks your permissions after login." Where authentication asks "who are you," authorization asks a completely different question, "given that I already know who you are, what am I going to let you do." The slide's own example makes the ordering explicit in its phrasing, "the authenticated user," meaning authorization is a check that only makes sense to perform on someone whose identity has already been established. A logged in, perfectly legitimate Gmail user is still not allowed into Gmail's internal admin panel, not because the system doubts who they are, but because being that particular, ordinary user simply does not come with admin level permissions attached.

The phrase "after login" in the slide's third bullet is doing real work. Authorization is not a one time event the way a login is, it is a check that can, and often does, get repeated on every single request that touches something sensitive, a specific route, a specific resource, a specific action. Every time a request comes in for something that requires a particular permission, the question "is this specific, already identified user actually allowed to do this specific thing" gets asked again.

## How the two connect to a JWT once one exists

The slides do not spell this connection out explicitly beyond the payload bullet mentioning "roles" as one of the things a token can carry, but it is the natural bridge between this note and the previous one, and it is worth making concrete. Once a server has authenticated a user and issued them a signed token, that token's payload is a convenient place to also carry the information authorization checks will need later, most commonly a role or a list of permissions alongside the user's id. A server handling a later request can then do both checks using the same token: verifying the signature answers "is this a genuine, unmodified token, so I can trust who it says the user is," which is the authentication half, and then reading the role or permission claims out of that already trusted payload answers "is this particular user allowed to do the specific thing they are asking to do right now," which is the authorization half. In a real NestJS implementation, these two checks typically show up as two different pieces of code working together, something like a guard that verifies the token to establish who the user is, and a separate guard or decorator that then checks that user's role before letting the request continue. [04-what-a-real-implementation-would-look-like.md](04-what-a-real-implementation-would-look-like.md) sketches what those two pieces would look like if this project actually had them, since as with everything else covered so far, no such guard exists anywhere in this repo today.
