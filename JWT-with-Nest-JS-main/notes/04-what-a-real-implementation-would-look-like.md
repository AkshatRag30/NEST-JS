# 04. What a Real Implementation Would Look Like

## Everything below is illustrative, not present in this repo

This note is different from the other three in that it is not describing anything you can currently open and read in this codebase. Nothing that follows exists in `src`, no such files, no such folders. It is a sketch, based on the standard, well documented conventions of `@nestjs/jwt` and `passport-jwt`, of what it would actually take to turn this exact scaffold (the plain `AppController`, `AppService`, and `AppModule` covered in the first note) into an application that genuinely does the login and token verification flow the slide deck describes. Treat this the way you would treat a recipe you have not cooked yet, useful for knowing what is involved and what order things happen in, not a description of a finished dish sitting in this repo already.

## Packages you would need to add

None of these currently appear in `package.json`. You would add `@nestjs/jwt` (NestJS's own thin wrapper for signing and verifying tokens), `@nestjs/passport` and `passport` (NestJS's integration with the widely used Passport authentication middleware for Node.js), `passport-jwt` (the specific Passport strategy that knows how to pull a JWT out of a request and verify it) along with its type definitions `@types/passport-jwt`, and something for password hashing, most commonly `bcrypt` (or the pure JavaScript `bcryptjs` if you wanted to avoid a native build step). You would also, realistically, want `@nestjs/config` fairly early on, since a JWT signing secret should live in an environment variable rather than being hardcoded into source, and this project currently has no configuration setup of any kind, not even that.

## A place to store users

The login step needs something to check a submitted email and password against, which means you need users to exist somewhere before you can authenticate any of them. The simplest possible version, matching the spirit of a small teaching project, would be a `UsersModule` with a `UsersService` holding a plain in memory array of user objects, each with an id, an email, and a hashed password, the same "hand rolled array inside a service" pattern you would see in a beginner CRUD project before a real database gets introduced. A more complete version would back that with an actual database instead, which this project also does not have. Either way, this piece would need to exist before an auth module could check anything against it.

## `AuthModule`, `AuthService`, and `AuthController`

A new `AuthModule` would import `UsersModule` (to look up users) and `JwtModule`, configuring the latter with `JwtModule.registerAsync()` so the signing secret and token expiration come from `ConfigService` rather than being written directly into the module. `AuthController` would expose one new route, a `POST /auth/login` endpoint, taking a small DTO with `email` and `password` fields (validated the same way any other DTO in a NestJS project is, with `class-validator` decorators and a global `ValidationPipe`, even though this scaffold does not currently use pipes or DTOs for anything either). `AuthService` would hold two methods worth naming directly: `validateUser(email, password)`, which looks the user up by email and then uses `bcrypt.compare()` to check the submitted plain text password against the stored hash (never comparing plain text passwords directly), and `login(user)`, which builds a payload object, typically something like `{ sub: user.id, email: user.email, roles: user.roles }` (the `sub` field, short for "subject," is the conventional JWT claim name for whichever id identifies the token's owner), and calls `this.jwtService.sign(payload)` to produce the actual token string, then returns it to the client, exactly matching the "if valid, the server generates a JWT token and sends it to the user" step from the login flow in the second note.

## `JwtStrategy`, the piece that verifies incoming tokens

This is the code that plays the role of "server verifies the token to authenticate the user on each request" from that same flow. A `JwtStrategy` class would extend `PassportStrategy(Strategy)` from `passport-jwt`, configured to pull the token out of the `Authorization` header of incoming requests (the conventional format being `Authorization: Bearer <token>`) and to verify it using the same secret `JwtModule` was configured with. Its `validate(payload)` method receives the already verified, already trustworthy payload (Passport only calls this method after confirming the signature checks out) and simply returns whatever should end up attached to `request.user` for the rest of that request's lifetime, typically the payload itself or a freshly looked up user record.

## Guards, protecting routes, and the authorization half

With a strategy in place, a `JwtAuthGuard` extending `AuthGuard('jwt')` from `@nestjs/passport` becomes a reusable guard that can be attached to any route with `@UseGuards(JwtAuthGuard)`, rejecting the request outright if no valid token is present and otherwise letting it through with `request.user` populated. This is the authentication half described in the third note, confirming who is making the request. The authorization half, deciding what that already identified user is allowed to do, would typically be a second, separate guard, something like a `RolesGuard` paired with a custom `@Roles('admin')` decorator that uses Nest's `Reflector` to read metadata off the route handler and compare it against the roles sitting in `request.user`. Stacking both guards on a sensitive route, `@UseGuards(JwtAuthGuard, RolesGuard)`, is a fairly direct, literal translation of the slide deck's own example: only a request that both proves who it is and turns out to hold the right role would ever reach something like an admin panel route.

## Where to actually see this built

All of the above is a description of shape, not a walkthrough of real, tested code, and building it out correctly (handling token expiration and refresh, hashing edge cases, error responses for expired or malformed tokens, and so on) is more involved than this sketch lets on. If you want to see these same ideas, authentication, authorization, JWT signing, and JWT verification, implemented as actual, working NestJS code, look at the sibling project in this same parent folder, `JWT-Auth-with-Mongo-DB-Nest-JS-main`. That project has a real auth module, a real JWT strategy, a user schema backed by MongoDB, and real login and protected routes, everything this note only sketches out in the abstract.
