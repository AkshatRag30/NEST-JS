# 02. JWT Structure and How It Works

## What the slides say a JWT is

The deck introduces JWT plainly, on the slide titled "JWT (JSON Web Token)": it is "a compact, URL-safe token used to securely transmit information between parties." The next bullet shows you what one actually looks like on the wire, starting with the characters `eyJhbGciOiJI.........`, and the slide after that tells you what is inside one, "encoded info like user ID, email, roles, etc." That is the entire JWT specific content in the deck, three short bullets. It is accurate as far as it goes, but a beginner needs a bit more to actually understand why a JWT looks the way it does and why that odd `eyJ...` prefix shows up every single time. The rest of this note fills that in using standard, well established JWT knowledge, since the slides themselves do not go past those three bullets.

## The three part structure

Every JWT is a single string made of three sections separated by two dots, written as `header.payload.signature`. That `eyJhbGciOiJI...` text the slide shows you is the start of the header section, and `eyJ` is not a coincidence, it is what you get almost every time you base64url encode a JSON object that starts with `{"`, since `{"` happens to encode to that exact character sequence. That is a small but genuinely useful thing to recognize: any string that starts with `eyJ` is very likely base64url encoded JSON.

The header is a small JSON object, typically containing two fields, `alg`, the algorithm used to sign the token (a common value is `HS256`, meaning HMAC using SHA-256), and `typ`, which is simply the string `"JWT"`. The payload is the second section, and this is where the "encoded info like user ID, email, roles" from the slide actually lives. It is also a JSON object, and the individual pieces of data inside it are conventionally called claims. There is no fixed list of claims a JWT must contain, an application is free to put whatever identifying information it needs into the payload, a user's id, their email, a list of roles, an expiration timestamp, and so on. The signature is the third section, and unlike the header and payload it is not simply an encoded piece of data, it is the output of a cryptographic signing operation, explained next.

## Encoded, not encrypted

This is one of the most commonly misunderstood things about JWTs, and it matters enough to state directly even though the slide deck does not spell it out explicitly. The header and payload are base64url encoded, not encrypted. Base64url encoding is a reversible, non secret transformation, anyone who gets hold of a JWT, including a user's own browser or a malicious party intercepting network traffic, can decode the header and payload sections and read their contents in plain text, without needing any secret key at all. You can paste any JWT into a public decoder site and immediately see the user id, email, and roles sitting right there in readable JSON. The practical consequence is that a JWT payload should only ever contain identifying information that is safe for the token holder (and anyone who intercepts it) to read, never a password, never a secret, never anything genuinely sensitive.

## Signing, and why it makes the token trustworthy

If the payload can be read by anyone, what actually stops someone from just editing it, for example changing their own `role` claim from `"user"` to `"admin"`, and sending the token back? This is exactly what the signature section prevents. When the server first creates a token, it takes the encoded header and the encoded payload, joins them with a dot, and runs that combined string through a signing algorithm together with a secret key that only the server knows. The result of that operation becomes the third section of the token. Because that secret key is never shared with the client and is not part of the token itself, nobody outside the server can produce a signature that matches a tampered header or payload.

Verification works by running the same operation in reverse. When a request comes in carrying a JWT, the server takes the header and payload out of that token, recomputes what the signature should be using its own secret key, and compares that freshly computed signature against the signature actually attached to the token. If they match, the server knows two things with confidence: the token really was issued by this server (or another party holding the same secret), and nothing in the header or payload has been altered since it was signed, because changing even a single character of either section would produce a completely different signature. If they do not match, the token is rejected outright. This is what the slide's phrase "server verifies the token" is actually describing under the hood.

## The login flow, from the slides

The final slide, titled "How JWT Authentication Works," lays out the flow as a short sequence, and it is worth quoting closely since it maps directly onto how a real implementation would be structured:

User sends email and password to login. Server verifies credentials. If valid, the server generates a JWT token and sends it to the user. The user sends that token with every request, in headers. The server verifies the token to authenticate the user on each request.

Walking through what each step means in practice: the first two steps are a normal login request, the kind of thing you would build with a plain `POST /login` route that checks a submitted email and password against stored user data. The third step is the moment a JWT actually enters the picture, once the server is satisfied the credentials are correct, it builds a payload (typically containing at least the user's id) and signs it as described above, then sends the resulting token string back to the client in the login response. The fourth step describes what happens on every subsequent request the client makes to any protected route: instead of logging in again, the client attaches that same token to the request, conventionally in an HTTP header. The fifth step is the server side counterpart, on each of those later requests the server pulls the token back out, verifies its signature the way this note just described, and if it checks out, treats the request as coming from whichever user id sits in that token's payload, no database lookup for a session required.

That last point is worth calling out even though the slide does not use the word for it: this flow is what people mean when they call JWTs "stateless" authentication. A traditional session based login stores something on the server (a session record) that has to be looked up on every request. A JWT instead carries everything the server needs to trust it, its own claims plus its own signature, so the server can verify a request without keeping any per user state in memory or in a database at all. The tradeoff, not covered in this slide deck, is that this makes revoking a single token before it naturally expires genuinely harder, since the server is not tracking which tokens are still "active" anywhere.

## What this repo does with any of this

Nothing, and it is worth being direct about that here rather than leaving it implied. As covered in the previous note, there is no login route, no token signing code, and no verification logic anywhere in `src`.
