# 06. Perks, Claiming, and the Admin Side

## What a perk actually is, and why there are two tables for it

A perk is a reward a reputation score and tier unlock, and `PerkEntity` (`tbl_perk`) is flexible enough to represent several very different kinds of reward through one `perkType` enum, `PROMO_CODE`, `NFT_TOKEN`, `WHITELIST`, `EARLY_ACCESS`, `EXCLUSIVE_CONTENT`, `COUPON`, and `USDT`. Every perk carries a `minReputationScore` and a `tierRequired`, and both are checked independently on claim, so a perk can in principle demand a numeric score threshold and a tier floor that do not perfectly line up with each other.

Coupons, though, also live in a second, newer table, `PerkCouponEntity` (`tbl_perk_coupon`), which links out to a real `CouponEntity` rather than storing a bare code string the way `PerkEntity.couponCode` does. `AdminPerkCouponController`'s own comment states plainly why this exists as a separate path, creating one of these creates a real row in `tbl_coupons` with `isPerkCoupon: true` and a linked perk coupon record, transactionally, giving reputation gated coupons the exact same coupon usage limits, TLD restrictions, and status machinery every other coupon in the platform already has, rather than reinventing that logic a second time inside the perk system. The catalog endpoint, `PerkRepository.findAllActivePerks`, has to reconcile both tables at once with a raw SQL `UNION ALL`, one branch selecting from `tbl_perk` and a second branch, included only when no partner filter is active and the type filter is either absent or explicitly `COUPON`, selecting from `tbl_perk_coupon` joined to `tbl_coupons`.

## The catalog adapts to whether you are logged in

`GET /perks` uses `OptionalAuthGuard`, a guard that authenticates a bearer token if one is present but never rejects the request for lacking one, `handleRequest` simply returns `null` on failure instead of throwing. An anonymous caller gets every active perk with `isUnlocked: false` on all of them and `pointsNeeded` equal to the raw `minReputationScore`. A logged in caller gets their real score and tier fetched once, then every perk in the page is checked against it in memory, `isUnlocked` requires both the score and the tier to clear, and `isClaimed` is answered by one query that unions across three different claim tables at once, `tbl_perk_claim`, `tbl_usdt_claim`, and `tbl_perk_coupon_redemption`, matched by either the user's id or their primary domain id, since a domain that changes owners should not let the new owner see the old owner's claims as their own.

Perk catalog text can also come back translated, `localizePerksList` batches every distinct title, description, and partner name across a whole page of results into a single translation call rather than one call per perk, caches the translated result for seven days keyed partly on the perk's own `lastChangedDateTime`, and, if the translation call itself fails, falls back to the original English text for that page without ever writing a broken result into the cache, so a transient outage in the translation service degrades gracefully instead of poisoning what gets served on the next request.

## Claiming, one flow per perk type

`UserPerkService.claimPerk` starts with two checks that apply no matter what kind of perk is being claimed, whether the daily reputation cron is currently running, refusing with a 503 if so, and a rate limit of five claims per user per rolling hour. Past that gate, the flow branches hard by `perkType`, and each branch is written to survive concurrent requests for the same scarce resource.

A `COUPON` perk just reveals its fixed `couponCode` and records a claim row, since the code itself is not consumed from any pool, everyone who is eligible gets the same string. A `PROMO_CODE` perk instead dequeues one row from a per perk pool table, `PerkCodePoolEntity`, inside a single database transaction that checks for an existing claim, locks and claims one unclaimed code with `pessimistic_write`, and inserts the claim row, all before the lock is released, specifically so a second concurrent request cannot dequeue a code that then goes unused because it lost the insert race, the comment on this method calls that scenario out directly as the bug this transaction shape is built to avoid.

A `USDT` perk requires a wallet address and network the user actually owns, verified against their connected wallets first, then runs supply, expiry, and duplicate checks a second time inside a transaction holding a pessimistic write lock on the perk row itself, because the first checks outside the transaction are only an early exit for the common case, the ones that actually matter are the ones re run under the lock. A successful USDT claim does not pay anyone automatically, it inserts a `PENDING` row in `UsdtClaimEntity` and emails an admin, `AdminPerkController`'s `PATCH /admin/perks/usdt-claims/:id/pay` is the manual step that later marks it `PAID` with an optional transaction hash and notes, the same "record it, then a human closes the loop" pattern seen throughout the affiliate payout flow. A newer `tbl_perk_coupon` perk (one that was not found in `tbl_perk` at all) is routed to a dedicated `claimPerkCoupon` method that mirrors the same locked, re validated transaction shape, just writing a `PerkCouponRedemptionEntity` row instead of a `PerkClaimEntity` one.

Every one of these insert paths also catches a raw Postgres unique violation, code `23505`, as a legitimate outcome rather than a bug, if the insert collides with an existing claim because two requests genuinely raced each other, the handler looks up the row that won and returns it as an "already claimed" success response instead of surfacing a database error to the client.

## Validating a coupon before you actually use it

`validateCouponUsage` is a separate endpoint that exists to answer one specific, practical question before checkout, has this affiliate or perk coupon code already been spent by this exact user. It re runs the full eligibility chain for the perk, but treats hitting the "already claimed" `ConflictException` as the expected, successful path here rather than an error, since the whole point of this call is to check a coupon the user has already claimed. Once it has the real coupon code in hand, it queries `DomainOrderEntity` directly for any order by this user that used that exact promo code, and answers accordingly, this is the one place in the perk system that reaches directly into the commerce side of the codebase to check real purchase history rather than staying inside its own tables.

## The admin side, and the routing trap its own comment calls out

`AdminPerkController` covers full CRUD on perks, bulk activate, deactivate, or tier change across many perks at once, promo code pool management, and both USDT claim and coupon redemption oversight, all gated behind `AccessTokenGuard` and `SuperAdminAccessGuard` together. One structural detail is worth carrying forward if this controller is ever extended, its own comment flags it directly, static routes like `coupon-redemptions` and `usdt-claims` have to be declared before the `:id` wildcard route, because Nest matches routes in declaration order and would otherwise treat the literal word `usdt-claims` as if it were a UUID being passed to `GET /admin/perks/:id`. `getAnalytics` is the one read heavy admin endpoint worth knowing about directly, it returns every perk's supply remaining and total claim count in a single query using a correlated subquery per perk row rather than fetching perks and claims separately and joining them in application code, sorted so the most claimed perks surface first.
