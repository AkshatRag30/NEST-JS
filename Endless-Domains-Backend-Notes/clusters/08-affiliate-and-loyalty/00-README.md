# 08. Affiliate and Loyalty

## What this cluster covers

This cluster is actually two separate businesses living side by side in the same part of the codebase. One is a classic referral program, a person gets a code, shares it, and earns a cut when someone they referred buys a domain. The other is a gamified loyalty system built for a Web3 audience, where holding one of the company's own `.og` domains lets you check in daily, build a reputation score out of your onchain activity, and redeem that score for perks. They do not share a database table or a business goal, but they share a folder tree, `reputation-gm-perk`, and a family of similarly spelled folders, `affilate` and `affiliate-user`, and untangling both of those is most of the point of this cluster.

Three top level component folders live here. `affilate`, spelled without the second "i", holds three submodules, `key-managment` (the actual referral code entity and its admin lifecycle), `user-activity-managment` (the click and conversion tracking that turns a code into a paid commission), and `affiliate-user-dashboard-managment` (the aggregated dashboard an affiliate sees). `affiliate-user`, spelled the normal way, is a separate, later addition that turned "being an affiliate" into a proper role on a user's account, complete with registration, payout requests, and a running ledger of what has been paid out. `reputation-gm-perk` is the loyalty side, three more submodules, `gm` (the daily "good morning" check in), `reputation` (the score built from a user's wallets, domains, GM streak, and NFT and contract activity), and `perk` plus `perk-admin` (the catalog of rewards that score can unlock, and the admin tooling to manage it).

## What's familiar here versus what's genuinely new

A referral program is not a new idea to build against from the frontend. A registration form, a dashboard with some totals and a chart, a payout request form, all of that is shape you have already built or consumed. What is less familiar is how much of this particular referral system's correctness lives in a single unglamorous table, `affilate_user_activities`, and in the SQL that groups rows in it by action name. There is no separate "conversion" event fired by the payment flow, a sale gets attributed to an affiliate key because the frontend logged a `Payment Success` activity row carrying the order id inside a free text payload string, and the backend later parses that string with a regular expression to line it up with a real, completed order. That is a fragile looking mechanism doing a genuinely important job, and it is worth reading closely rather than assuming a cleaner event system sits underneath it, because it does not.

The loyalty side is the part with no obvious frontend precedent. A "daily check in" sounds like it could be a database flag flipped by a button click, but here it means the user's wallet actually has to send a real transaction to a smart contract, and the backend fetches that transaction from the chain itself, checks the receipt succeeded, decodes an event log to confirm who sent it and which domain it names, and only then lets the streak advance. The reputation score sitting on top of that is not a static number either, it is recalculated by a nightly cron across every user with a stale score, calling out to Alchemy for wallet activity on five chains, and the whole batch is guarded by a database flag that freezes perk claims while it runs, specifically so nobody can claim a limited supply perk using a score that is about to be recalculated out from under them. None of that has a tidy frontend analogy, it is a genuine backend discipline, treating a number a user can see on their own dashboard as something that has to be earned honestly and cannot be spoofed by replaying an old transaction or racing a batch job.
