# 05. Landing Page Marketing Content

## The biggest folder in this cluster, and why it looks the way it does

`landing_page` holds roughly sixty files, more than any other folder covered in this cluster, but almost all of that size comes from repetition rather than genuine complexity. Six independent sub-features live inside it, `count-analytics`, `faqs`, `get-started-simple-steps`, `testimonials`, `tld-analytics`, and `top-domain`, and every one of the first four follows the exact same shape, an entity extending the shared `BaseEntity`, a repository extending `BaseAbstractRepository` that hand rolls its own insert, update, and delete with TypeORM's query builder, a service that wraps the repository and translates a Postgres duplicate key error into a friendly `BadRequestException`, and a controller exposing a small REST surface under `/landing-page/*`. Once that shape is understood from reading one sub-feature closely, the other three are mostly a matter of matching field names to what they represent on the actual marketing site.

## The four repeated CRUD features

`count-analytics` (`/landing-page/count-analytics`) manages the big numeric stat counters a marketing site likes to show, a `title` and a `value` pair, meant for things like a total domains registered figure. `get-started-simple-steps` (`/landing-page/simple_steps`) manages the ordered, numbered steps in a "how to get started" section, each with a `title`, an `instruction`, and a `position` that carries its own unique constraint so two steps can never claim the same slot. `faqs` (`/landing-page/faqs`) manages the site wide frequently asked questions list, each with a `question`, an `answer`, and a `position`. Its entity carries one extra column worth quoting because of what its own comment says about it:

```ts
@Column({ nullable: false, default: false, comment: 'this column is used to check if the question is asked by user or they generated by the admins.' })
default: boolean;
```

Nothing else in this folder, or anywhere else searched in this cluster, ever creates a user submitted FAQ, so whatever pipeline was meant to let real user questions flow into this table either lives entirely outside this cluster or was never finished. `testimonials` (`/landing-page/testimonials`) manages customer quotes, each with a `name`, `role`, `company_name`, `testimonial` text, `position`, and an optional `img`, and its write endpoints accept a multipart file upload handled by `FilesInterceptor` and pushed to S3 through the shared `S3Service`.

## The authorization story is the real finding in this folder

Reading all four write controllers side by side turns up a genuine, checkable inconsistency. `count-analytics` and `get-started-simple-steps` protect every write route the same way:

```ts
@UseGuards(AccessTokenGuard, AdminTokenGuard)
```

`AdminTokenGuard` is not a JWT check at all, it is a plain header equality test against a static configuration value:

```ts
if (headers['admin-token'] == this.ADMIN_TOKEN) { return true; }
```

Combining that with `AccessTokenGuard` (which does verify a real JWT) is a real, if unusual, defense in depth choice, a caller now needs both a valid session token and a separate static shared secret. But `faqs` and `testimonials` do not use either guard on their create, update, or delete routes at all, nothing sits in front of them:

```ts
@Post()
@HttpCode(HttpStatus.OK)
public async addFAQ(@Body() faqsData: CreateFAQsDto): Promise<Response> {
```

That is the whole decorator list on `FaqsController.addFAQ`, no `@UseGuards` anywhere above it, and the same is true for `updateFAQ`, `deleteFAQ`, and every write route on `TestimonialsController`. As written, anyone who can reach this API can add, rewrite, or delete any FAQ or testimonial on the public marketing site without any credential at all. This sits in the same folder, wired into the same `LandingPageModule`, right next to two sibling features that do lock their writes down, which makes it hard to read as an intentional design decision rather than an oversight.

## A second, smaller inconsistency worth knowing about in testimonials

`TestimonialsService.addNewTestimonial` uploads a new image using `this.S3_IMG_BUCKET_NAME`, but `updateTestimonial` uploads using `this.S3_PUBLIC_IMG_BUCKET_NAME`, a different configured bucket:

```ts
// addNewTestimonial
const fileLocation = await this.s3Service.uploadFile(img[0], 'test/testimonial/', this.S3_IMG_BUCKET_NAME);
// updateTestimonial
const fileLocation = await this.s3Service.uploadFile(img[0], 'test/testimonial/', this.S3_PUBLIC_IMG_BUCKET_NAME);
```

Both code paths then build the public facing URL the same way, using `S3_PUBLIC_IMG_BUCKET_NAME` regardless of which bucket the file actually landed in. If those two environment values ever point at genuinely different buckets, updating an existing testimonial's photo would upload the file to one place while the entity ends up pointing at a URL built for the other, a real, if narrow, bug worth flagging rather than assuming it is intentional.

## The two read only features are simpler, and public

`tld-analytics` (`/landing-page/tld-analytics`) has no entity of its own at all, its controller and service are a thin, single method passthrough that calls straight into the domain module's `DomainDetailServiceInterface.getTldAnalyticsData()`. It exists in this folder purely to give the landing page's own analytics widget a stable, dedicated route, while the real query logic lives with the domain data it is describing. `top-domain` (`/landing-page/top-domain`) does have its own entity, tracking `domain_provider`, `item`, `total_volume`, and `total_owner`, and its one query is worth a look because of the technique it uses:

```ts
async findLatestTopDomain(): Promise<TopDomainEntity[]> {
    return await this.repo.createQueryBuilder('main').select('main.*')
        .innerJoin(
            (subQuery) => subQuery.select(['tbl.domain_provider', 'max(tbl."lastChangedDateTime") as max_date'])
                .from(TopDomainEntity, 'tbl').groupBy('tbl.domain_provider'),
            'sub_tbl',
            'main.domain_provider = sub_tbl.tbl_domain_provider and main."lastChangedDateTime"= sub_tbl.max_date'
        ).getRawMany();
}
```

This joins the table against a subquery of its own most recent timestamp per provider, which is a standard way to pull only the latest snapshot row for each group out of a table that otherwise accumulates one row per update over time. Both of these features only expose a `GET` route, there is no create, update, or delete endpoint anywhere in this folder for either one, which means whatever process populates `tbl_top_domain` runs from somewhere outside this cluster entirely, most likely a scheduled job living with the domain or blockchain integration code.
