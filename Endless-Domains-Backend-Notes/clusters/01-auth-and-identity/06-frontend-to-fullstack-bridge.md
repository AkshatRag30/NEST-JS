# 06. From Frontend to Fullstack: What You Already Know vs What Is Actually New Here

This note is deliberately short. It exists to point at the exact lines in the rest of this cluster that correspond to things you have almost certainly already done from the frontend, and to be specific about what is genuinely new on the server side of each one.

## What you already know

You have called a login endpoint with an email and password and gotten a token back. You have stored that token somewhere (`localStorage`, a cookie, a state management store) and attached it to later requests, usually as an `Authorization: Bearer <token>` header. You have redirected a user to Google, gotten them back with some kind of code or token, and sent that along to your own backend to finish the login. You have seen a 401 response and known it meant "log this person out and send them to the login page." All of that is real, transferable knowledge, and it maps directly onto this codebase, `POST /auth/login` in [01-password-login-and-jwt-tokens.md](01-password-login-and-jwt-tokens.md) is exactly the endpoint you have called a hundred times before, and `POST /google-auth` in [02-oauth-google-and-twitter.md](02-oauth-google-and-twitter.md) is exactly the "send the OAuth token to my own backend" step you have written before.

## What is actually new: the part that happens after you send the request

The part you have not had to build yourself is everything covered in the rest of this cluster, how that access token gets *checked* on every subsequent request, and how a new one gets *issued* without asking the user to type their password in again.

Checking the token is `AccessTokenGuard`, a one line class wrapping Passport's `AuthGuard('jwt')`, which under the hood runs `AccessTokenStrategy.validate()` against every route decorated with `@UseGuards(AccessTokenGuard)`. On the frontend, a token is just an opaque string you attach to a header and never look inside. On the backend, that string has to be cryptographically verified against a secret only the server holds (`JWT_ACCESS_TOKEN_SECRET`, see the first note in this cluster for exactly how, and how inconsistently, that secret gets read), and only after that verification succeeds does the rest of the request even get a `req.user` to read from.

Refreshing is the part with no obvious frontend equivalent at all. A frontend developer's mental model is often "the token just... stays valid," but in this codebase an access token deliberately expires quickly, and the actual mechanism for staying logged in without re-entering a password is `GET /auth/refresh-token`, a second, longer lived refresh token, hashed with `argon2` and stored against the user row, that gets exchanged for a brand new access and refresh token pair, with the old refresh token immediately invalidated the moment the new one is issued. This is the piece worth spending real time understanding if you take nothing else from this cluster, it is the single most common thing a frontend integration gets subtly wrong (calling the login endpoint once and then being surprised when the access token stops working twenty minutes later with no refresh call ever wired up on the client side to replace it).

Logout, from the frontend, usually means "delete the token from local storage." Here, `AuthService.logout` also does real, server side work, `removeRefreshToken` nulls out the stored hash so that even a refresh token the client somehow retained can never be exchanged again, meaning logout in this system is enforceable server side, not merely a client side convention that a still-valid token could ignore.

Email verification is a similar shift in perspective. From the frontend, clicking a "verify your email" link is just navigation. From the backend's side, that link's `?token=` value is a signed JWT with its own secret and its own expiration, and the route it lands on (`GET /email-verification/verify`, see the fourth note in this cluster) has to decode it, distinguish an expired token from a tampered or malformed one, and only then flip a boolean on the user's row, before finally redirecting the browser onward, the `@Redirect()` decorator covered in that note is Nest's mechanism for a route handler to decide where to send the browser next, worth learning on its own since it comes up anywhere a backend needs to hand control back to a frontend page after doing some server side work first.

Finally, the wallet based login in this cluster's third note is worth sitting with even if you never touch Web3 again, because "prove you own this without a password" is a genuinely different problem than password checking, and seeing a real, working implementation of a nonce and signature challenge, plus a real, verified instance of that same idea implemented incorrectly a few methods below it for Solana, is a concrete way to build intuition for why authentication code in general deserves this level of scrutiny rather than being assumed correct just because it compiles and returns the right shape of response on the happy path.
