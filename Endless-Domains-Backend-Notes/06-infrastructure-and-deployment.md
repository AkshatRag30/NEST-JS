# 06. Infrastructure and Deployment

## Why a frontend developer should care about this file at all

Every reference project before this one, and every feature module in this codebase, ends at "the app runs." This note is about what happens after that, where it actually runs, how it gets there, and how its configuration reaches it, because that gap, between code that works on your machine and code that serves real traffic, is exactly the part of the job a frontend background usually has the least exposure to, and exactly the part most worth deliberately learning if fullstack or backend roles are the goal.

## The deployment shape, read from `terraform/main.tf`

Terraform is a tool for describing real cloud infrastructure as code, the same way a NestJS module describes a piece of an application as code, run `terraform apply` and it creates, updates, or destroys real AWS resources to match what the file says should exist. This project's `terraform/main.tf` wires together eight modules, each one living in `terraform/modules/<name>`, and the order they depend on each other in tells you the actual shape of the deployment.

`module "ssm"` runs first, and it takes nearly every sensitive configuration value the app needs, database credentials, API keys for every third party integration, JWT secrets, and pushes them into AWS Systems Manager Parameter Store (SSM), a secure, centrally managed place to store configuration, closely related in spirit to the Secrets Manager service `SecretsService` reads from at runtime, covered in [03-configuration-and-secrets.md](03-configuration-and-secrets.md). `module "dns"` and `module "cloudflare_init"` set up the actual domain records and a TLS certificate, this is the part of "how does `endlessdomains.io` actually point at a running server" that a frontend developer has usually never had to touch, DNS records, certificate validation, and a CDN or DNS provider (Cloudflare here) all need to agree with each other before a browser can successfully load the site securely. `module "lb"` creates a load balancer, the component that receives all incoming internet traffic and distributes it across however many copies of the app are actually running, so the system can handle more traffic by running more copies rather than one single, ever growing server. `module "s3"` provisions the file storage bucket the app's own `@aws-sdk/client-s3` dependency uploads to (profile pictures, exported files, and the like, covered in the relevant cluster notes). `module "ecs"` is the actual compute layer, ECS (Elastic Container Service) is AWS's service for running Docker containers without managing individual servers yourself, and this module is where the entire Joi validated environment variable list from `app-env-validation.ts` reappears, as Terraform variables, being handed to the running container.

Two modules, `rds` (a managed Postgres database) and `elasticache` (a managed Redis cache), are present in the codebase but entirely commented out in `main.tf`. That is worth sitting with rather than skimming past, it tells you this team either provisions its real Postgres database and cache some other way (an existing, already running instance, a different tool, or a manual setup outside this particular Terraform configuration) or deliberately has not turned this specific piece of infrastructure on yet. Either way, this is exactly the kind of detail a real infrastructure review would flag as worth confirming with whoever owns deployment, never assume commented out infrastructure code is simply dead or simply forgotten, ask.

## The container itself

`scripts/build_backend.sh`, `scripts/deploy.sh`, `scripts/start_backend.sh`, and `scripts/install_dependencies.sh`, alongside a second `run/deploy.sh`, are the shell scripts that actually build and ship a new version of the app onto that ECS infrastructure, worth reading directly since shell scripts like these are usually the most honest, unfiltered description of a real deployment process available anywhere in a codebase, more so than any documentation, because they are the thing that actually runs.

## Local development, by contrast

`db/01-init.sh` is a small script that creates a fresh local Postgres database (`CREATE DATABASE $APP_DB_NAME`), the kind of thing a Docker Compose setup or a local setup script would run once when spinning up a database container for local development, a much smaller, simpler cousin of the real, managed database this app talks to in production. `.husky/pre-commit` and `.husky/prepare-commit-msg` are Git hooks, small scripts that run automatically at specific points in your own local Git workflow (before a commit is created, and while its commit message is being written), commonly used to run linting or formatting automatically so broken or unformatted code never gets committed in the first place, worth opening directly to see exactly what checks this team has decided are important enough to enforce automatically rather than leave to hope.

## The one sentence version worth remembering

Code living in `src` describes what the application does. Everything in `terraform`, `scripts`, `run`, and `db` describes where it runs, how it gets there, and what has to be true about the outside world (a database, a domain name, a certificate, a load balancer) before it can serve a single real request, and a fullstack engineer is someone who is expected to have at least a working, if not expert, understanding of both halves, not just the first one.
