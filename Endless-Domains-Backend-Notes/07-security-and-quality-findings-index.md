# 07. Security and Quality Findings, Collected in One Place

## Why this file exists

Eleven separate agents each read one slice of this codebase in isolation (and six more read the October 2026 additions, collected in the update section at the end), and several of them found something genuinely worth a second look, a real gap, a piece of dead code, or an inconsistency between two similar features. Each finding is already written up in full, with real quoted code, inside its own cluster's notes. This file exists purely to collect them in one place, ranked roughly by how serious they are, so nothing gets lost across eleven different folders, and so you have one list to actually act on rather than eleven.

A note on tone before the list itself. Every one of these was found by reading real, live, production code for a real company, not a toy project, and every large, multi year codebase built by many people accumulates issues like this, that is normal, not a verdict on anyone's competence. The skill worth taking from this file is not judgment, it is the habit of noticing, and knowing what to do once you notice, which for anything below marked genuinely security relevant is simply this, tell whoever owns that part of the system, do not fix it quietly on your own without discussion, since a change to auth or payment code always needs a second set of eyes before it ships.

## Findings serious enough to raise with the team directly

The Solana wallet login path in `web3-auth.service.ts` never checks a cryptographic signature at all, unlike the Ethereum path, which correctly uses `ethers.utils.verifyMessage` (now `ethers.verifyMessage` after the ethers v6 upgrade). Anyone who knows a Solana address already tied to an existing account can log in as that user with no proof of ownership. Full detail in [clusters/01-auth-and-identity/03-web3-wallet-auth.md](clusters/01-auth-and-identity/03-web3-wallet-auth.md). This is a real authentication bypass.

The Unstoppable Domains webhook handler computes an HMAC signature and then never actually checks it, the comparison line is commented out, and the secret it computes that unused signature with is a literal string hardcoded in the source file rather than pulled from Secrets Manager the way every other secret in this app is handled. The main Stripe webhook, which confirms real domain purchase payments, performs no signature verification of any kind. Full detail in [clusters/09-events-and-webhooks/02-signature-verification-deep-dive.md](clusters/09-events-and-webhooks/02-signature-verification-deep-dive.md). A public webhook endpoint with no real verification can be called by anyone, not just the provider it claims to trust.

Several admin write endpoints, across FAQs, testimonials, static content, and a few search management routes, carry no authentication guard at all, sitting directly beside sibling endpoints in the very same controllers that are properly locked down. Full detail in [clusters/07-admin-cms-and-marketing/02-static-content-and-tld-metadata.md](clusters/07-admin-cms-and-marketing/02-static-content-and-tld-metadata.md) and [08-internal-search-analytics-and-event-tracking.md](clusters/07-admin-cms-and-marketing/08-internal-search-analytics-and-event-tracking.md).

The admin facing user management response DTOs in `user-rbac` return a user's password directly in the response body, the plaintext value at creation time, the bcrypt hash on login, while the ordinary consumer facing user DTO correctly has no password field at all. Full detail in [clusters/01-auth-and-identity/05-rbac-and-guards.md](clusters/01-auth-and-identity/05-rbac-and-guards.md).

## Real, worth fixing, but lower stakes

In the buy domain flow, reserving a listing and saving the actual purchase record happen as two separate, un-transacted writes. If the second write fails, the listing is left stuck "in progress" permanently with no purchase behind it, and nothing ever automatically revisits it. Full detail in [clusters/03-commerce-and-marketplace/03-domain-listing-and-buy-domain-secondary-marketplace.md](clusters/03-commerce-and-marketplace/03-domain-listing-and-buy-domain-secondary-marketplace.md). Across the whole commerce cluster, this is the only place a payment or order state change is genuinely vulnerable to a partial failure leaving bad data behind.

A Twitter OAuth consumer key and secret sit hardcoded in plain text in `twitter-auth-service.ts`. This is a real, leaked credential sitting in version control, even though the module itself is never actually imported into the running app today. Full detail in [clusters/01-auth-and-identity/02-oauth-google-and-twitter.md](clusters/01-auth-and-identity/02-oauth-google-and-twitter.md). A credential that is not currently reachable is still a credential that should be rotated and removed, since source history keeps it around indefinitely.

## Dead or dormant code worth knowing about, not urgent

`listener`, despite its name, is not a blockchain event subscriber, it is a generic cron job registry that is injected into `domain-order.service.ts` but never actually called anywhere in the codebase. [clusters/05-blockchain-infrastructure/09-listener-what-it-really-is.md](clusters/05-blockchain-infrastructure/09-listener-what-it-really-is.md).

The waitlist signup endpoint throws a fixed `ServiceUnavailableException` before running any of its own, fully built referral and abuse prevention logic, which sits commented out directly beneath the throw. This reads as a deliberate, temporary shutoff rather than an accident. [clusters/02-user-and-profile/05-waitlist-and-early-access.md](clusters/02-user-and-profile/05-waitlist-and-early-access.md).

The recaptcha guard's success path never actually returns `true`, but the guard is also never applied to any real route, so it is broken without currently being harmful. [clusters/01-auth-and-identity/05-rbac-and-guards.md](clusters/01-auth-and-identity/05-rbac-and-guards.md).

An `arb-integration` file contains a broken, fire and forget duplicate of a working call that already exists correctly in `ens-arb-bnb-domain-suggestion`, and a `bnb-integration` module exists but is empty. [clusters/06-chain-and-registrar-integrations/06-quirks-and-bugs-catalog.md](clusters/06-chain-and-registrar-integrations/06-quirks-and-bugs-catalog.md).

## Naming and organizational history worth understanding, not bugs at all

`affilate` (the misspelled folder) and `affiliate-user` (the correctly spelled one) are not a deliberate architectural split, the older `affilate` layer owns the real referral keys and activity tracking, the newer `affiliate-user` layer turned "being an affiliate" into a real account with payouts, and the two depend on each other in both directions, down to colliding on the same dependency injection token string in two unrelated modules. [clusters/08-affiliate-and-loyalty/03-affilate-vs-affiliate-user-the-split.md](clusters/08-affiliate-and-loyalty/03-affilate-vs-affiliate-user-the-split.md).

The internal, application wide event system built on `EventEmitter2` and a completely unrelated marketing CMS module that happens to also be named `events` are two different things that share a name by coincidence. [clusters/09-events-and-webhooks/03-internal-events-vs-external-webhooks.md](clusters/09-events-and-webhooks/03-internal-events-vs-external-webhooks.md).

`ud-billing` is not a payment gateway despite sitting among the payment integration folders, it is a super admin only analytics and revenue reconciliation dashboard reading data the real payment integrations already wrote. [clusters/11-payment-gateway-integrations/04-ud-billing.md](clusters/11-payment-gateway-integrations/04-ud-billing.md).

## The pattern worth taking away from this whole list

Notice how many of these findings are not "the code is wrong," but "the code is inconsistent with itself," one wallet type checks a signature and the other does not, one webhook verifies and another does not, one DTO leaks a password and its sibling does not, one folder pair looks like a planned split but is actually an accident of history. That inconsistency, not raw complexity, is the real signature of a large, real, multi year codebase built by many hands, and learning to hunt for exactly that kind of asymmetry, the same operation done two different ways in two similar looking places, is one of the highest leverage code reading skills you can build heading into a fullstack or backend role.

## Update from the October 2026 uat pull

Everything above was found against commit `a131b429`. This section adds what turned up while reading the forty five commits up to `uat` merge commit `dc1ba3e8`, mostly in the new [cluster 12, marketplace v2](clusters/12-marketplace-v2/00-README.md), plus the ethers v6 migration and a few older modules it touched. The same rules apply as before. Everything here was found by reading code and specs, nothing was run or reproduced, and anything security or money related should go to whoever owns it as a conversation, not as a quiet fix.

### First, the status of the original findings

None of the serious findings above were fixed by this update. The Solana wallet login in `web3-auth.service.ts` (`solanAuthenticate`, around line 263) still only checks that a nonce exists for the address and never verifies a signature, while the Ethereum path now calls `ethers.verifyMessage` (the v6 name for `ethers.utils.verifyMessage`) at line 124. The Unstoppable Domains and Stripe webhook verification gaps, the unguarded admin CMS routes, and the password in the `user-rbac` response DTOs are untouched, because none of those files changed. One related item did improve. Ethereum wallet login now rotates its nonce after a successful `authenticate`, so a captured login signature can no longer be replayed there, although `verifyAndUpdateWalletAddress` (`web3-auth.service.ts:147`) still never rotates its nonce. See [clusters/01-auth-and-identity/03-web3-wallet-auth.md](clusters/01-auth-and-identity/03-web3-wallet-auth.md).

One more existing credential was noticed during this pass. A live Infura project key is hardcoded inside the BNB RPC URL at `recent-domains/recent-domain.service.ts:54`. It belongs alongside the Twitter key above: rotate it and move it into the AWS secret. See [clusters/06-chain-and-registrar-integrations/05-not-actually-integrations.md](clusters/06-chain-and-registrar-integrations/05-not-actually-integrations.md).

### New findings serious enough to raise with the team directly

Cancelling a marketplace v2 listing does not actually cancel it. `OrderService` cancel (`order.service.ts:761`) only flips the row's status in Postgres and stops serving the signature. Anyone who fetched the signed order while it was active (any buyer, bot or indexer that called `GET /marketplacev2/orders/:orderHash`) can still submit it to Seaport and buy the domain at the old price until `endTime`, and the poller will then record that sale. The success message at line 782 tells the seller the listing is cancelled. A real on chain cancel needs Seaport's own `cancel` or `incrementCounter`, which the seller's wallet has to send. See [clusters/12-marketplace-v2/05-cancel-expiry-and-the-listing-expiry-scheduler.md](clusters/12-marketplace-v2/05-cancel-expiry-and-the-listing-expiry-scheduler.md) and [09-applying-seaport-and-domain-events.md](clusters/12-marketplace-v2/09-applying-seaport-and-domain-events.md).

The event poller is not safe with more than one process running, and production will run more than one. The cursor write at `poller/tick/chain-event-source-poller.service.ts:388` has no compare and swap, so two overlapping pollers can move the cursor backwards. This has already happened once. A comment in `config/chain-config.loader.ts` records that on 29 September 2026 a developer's local backend polled against the shared UAT database alongside the UAT server, the two kept overwriting the one cursor row, and "the cursor jumped backward". The fix was the `POLLER_ENABLED` flag, which stops accidental extra pollers but does not make two real ones safe. The guard against overlapping ticks (`tickInFlight`) is an in memory flag, so it only works inside one process. Meanwhile the ECS deployment allows 200 percent of desired tasks during a rolling deploy (`terraform/modules/ecs/main.tf:539`), so every deploy briefly runs two pollers. And if `POLLER_ENABLED` is missing from the secret, it falls back to on in production, so every PM2 process polls. The usual fixes are a database advisory lock or a conditional `UPDATE ... WHERE lastBlock = :expected`. See [clusters/12-marketplace-v2/08-the-onchain-event-poller-architecture.md](clusters/12-marketplace-v2/08-the-onchain-event-poller-architecture.md).

Chain re orgs deeper than five blocks would leave fake sales in the database permanently. Five confirmations (`poller/constants/poller.constants.ts:22`) is the only re org protection. If a deeper re org removes a fill, the order stays `filled` and the append only `SOLD` history and `SALE` transaction rows stay too, with nothing to reverse them. Polygon has had re orgs deeper than that historically. Reading up to the `finalized` block tag instead of `latest` minus five would close this. Same note as above.

Six legacy scheduled jobs silently stopped on `uat`. `CronModule` is commented out in `app.module.ts:177` (commit `836d5f89`). Verification email reminders, pending order reminders every five minutes, daily domain expiry emails, Freename mint finalization every thirty seconds, and the hourly wallet balance check no longer run. The wallet balance check was already broken, because `this.rpcUrl` is never assigned. Freename mints can now only be finalized through `POST /internal/freename/finilize` (`freename-internal.controller.ts:56`), which has no guard. If this ships to production as is, users stop getting expiry warnings with no error anywhere. See [clusters/10-ai-and-infra-utilities/05-cron-scheduled-jobs.md](clusters/10-ai-and-infra-utilities/05-cron-scheduled-jobs.md).

`AdminTokenGuard` now protects a dozen new `_health` routes, and its comparison is loose. At `src/@core/common/guards/admin-token.guard.ts:16` it compares the `admin-token` header to `ADMIN_TOKEN` with `==`. If `ADMIN_TOKEN` were ever missing from the secret, `undefined == undefined` is true, so any logged in user sending no header at all would pass. The comparison is also not constant time. These routes expose order validation internals, chain config and poller state. A strict `===`, a startup check that the token exists, and `crypto.timingSafeEqual` would fix all three. See [clusters/12-marketplace-v2/01-what-marketplace-v2-is-and-the-module-map.md](clusters/12-marketplace-v2/01-what-marketplace-v2-is-and-the-module-map.md).

Seaport counter bumps only produce a log line. When a seller calls `incrementCounter` on Seaport, every order they signed earlier becomes unfillable on chain, but `seaport-event-application.service.ts:301` only logs it, at `warn` level, which does not reach CloudWatch. Those listings stay active and servable, and buyers who try them waste gas on reverted transactions. A fill that fails the backend's own verification (line 103) is likewise only logged, so a domain that really sold can stay listed. See [clusters/12-marketplace-v2/09-applying-seaport-and-domain-events.md](clusters/12-marketplace-v2/09-applying-seaport-and-domain-events.md).

### Real, worth fixing, but lower stakes

Wallet proof nonces are not safe across processes or under concurrency. They live in the in memory cache, so a nonce issued by one ECS task is unknown to another, and all of them are lost on restart. The get and delete at `wallet-verification.service.ts:51` are two separate steps, so two concurrent submissions of the same proof can both succeed, which contradicts the code's own comment. The nonce is also consumed before the signature is checked, so a malformed request burns it. Separately, `RequireVerifiedWalletGuard` only checks freshness, so a wallet the user has just unlinked keeps its authority until the one hour window ends. See [clusters/12-marketplace-v2/02-wallet-verification-and-the-verified-wallet-guard.md](clusters/12-marketplace-v2/02-wallet-verification-and-the-verified-wallet-guard.md).

Several inputs reach the database or `BigInt` unchecked and produce 500s instead of 400s. A browse cursor reused after the sort changes fails in SQL (`order-cursor.util.ts:38`, `order.service.ts:1115`). `maxPrice=1.5` passes `@IsNumberString` and then fails on `::bigint`. `PERCENTILE_CONT` can return a fractional median ask that breaks client side `BigInt` parsing. The my* query DTOs have no maximum `limit`. A watchlist DELETE with a non UUID id is not run through `ParseUUIDPipe`. And `getAddress` throws outside a `try` for bad checksums in the watchlist and GM services. See [clusters/12-marketplace-v2/06-browsing-orders-filters-and-cursor-pagination.md](clusters/12-marketplace-v2/06-browsing-orders-filters-and-cursor-pagination.md) and [07-watchlist-listing-status-history-and-transactions.md](clusters/12-marketplace-v2/07-watchlist-listing-status-history-and-transactions.md).

Times are stored without a time zone. `createdAt`, `filledAt` and related columns are `timestamp`, not `timestamptz`, while cursors and stale event checks use UTC. On any server or laptop not set to UTC, pages can skip or repeat, and the poller's stale replay guard can wrongly ignore real transfers. A laptop in India writing to the shared UAT database is enough to trigger it. See notes 06 and 09 in cluster 12.

Chain errors are classified too broadly. `isRetryableChainError` (`src/@core/utils/retry/is-retryable-chain-error.util.ts:13`) retries every ethers `SERVER_ERROR`. That includes 401 and 403 from a revoked RPC key, and an `ownerOf` revert on a burnt token, so the user waits around five seconds and gets a 503 `CHAIN_UNAVAILABLE` instead of a clear rejection. Because passing this predicate replaces `retryWithBackoff`'s default, RPC 429s are no longer retried at all. In the poller, any error without a code (a `TypeError`, a missing column) counts as transient, so one bad block range can wedge the poller forever. See [clusters/12-marketplace-v2/04-creating-and-validating-an-order.md](clusters/12-marketplace-v2/04-creating-and-validating-an-order.md) and note 08.

Small correctness bugs in order data. `splitDomainNameAndTLD` takes the second label, so `pay.alice.crypto` is stored with TLD `alice` (`order.service.ts:655`, `helper.ts:57`). The `NAME_MISMATCH` check is case sensitive. Cancel writes history under the caller's user id rather than the order owner's. Expiry history records the sweep time instead of `endTime`. And `filledBy` is taken from the Seaport `recipient`, which can be an aggregator contract rather than the real buyer, so the buyer's purchase may be missing from "my purchases". See notes 04, 05 and 09 in cluster 12.

Startup became more fragile. A missing or malformed marketplace chain key, or a mismatch in the poller's event topic assertion, now stops the whole API from booting, including login and checkout. `.env.sample` lists the wrong key names, omits the `POLLER_*` keys and shows an invalid `FEE_BPS` of zero, so an environment built from it will not boot. See [03-configuration-and-secrets.md](03-configuration-and-secrets.md).

Important signals are logged where nobody will see them. `warn()` reaches the console only, and `debug()` reaches nothing outside it. The poller's `getLogs` failures, the alert for an order that sold after it was cancelled off chain, counter bumps, and every chain config fallback warning are invisible in CloudWatch. See [05-logging-and-observability.md](05-logging-and-observability.md).

Rate limiting is weaker than it looks. `ThrottlerModule` was never applied globally (there is no `APP_GUARD`), so the new public marketplace and `/market` routes have no throttling. The three `express-rate-limit` routes share one limiter instance, and therefore one counter per IP, and each process counts separately. `GET /marketplacev2/poller/health` is open to any logged in user, and every call costs a paid RPC request. See [02-high-level-architecture-and-bootstrap.md](02-high-level-architecture-and-bootstrap.md).

Market data numbers are approximations that the charts present as facts. USD volume is priced at today's CoinGecko price rather than the price at sale time, so thirty day volume moves with ETH. Only USDC, USDT and DAI count as stablecoins, and sales in any other token add to sales counts but not volume, which pulls averages down. "Daily" chart buckets are rolling twenty four hour windows ending at the current UTC hour, so in India they run from about 16:30 to 16:30. The newest hourly listing buckets are understated, which shows up as a false dip at the right edge. Figures from a failing collection are reused with no age limit. And the whole cache is in memory, so every deploy serves 503s until the jobs refill it, and it only works correctly with one instance per OpenSea key. See [clusters/12-marketplace-v2/10-opensea-market-data-pipeline.md](clusters/12-marketplace-v2/10-opensea-market-data-pipeline.md) and [11-market-endpoints-charts-and-the-frontend.md](clusters/12-marketplace-v2/11-market-endpoints-charts-and-the-frontend.md).

The ethers v6 migration left a few sharp edges. `@ethersproject/bignumber` and `@ethersproject/bytes` are still imported in three files but are not declared in `package.json`; they only arrive because `alchemy-sdk` depends on them. The older modules build `JsonRpcProvider` without `staticNetwork`, so a dead RPC can stall a request with retries every second instead of failing fast. v6 `getBlock` can return `null`, which would throw outside a `try` in deployment verification and GM verification. And `bnb-alchmey.serveice.ts:237` returns `result || null`, where the string `"0"` is truthy, so an unregistered label can overwrite an expiry with 1 January 1970. See [clusters/12-marketplace-v2/12-ethers-v6-migration-and-the-new-test-suite.md](clusters/12-marketplace-v2/12-ethers-v6-migration-and-the-new-test-suite.md).

Installs depend on private GitHub access. `@endlessdomains/order-builder` comes from a private repository, and `package.json` (`git+https`) and `package-lock.json` (`git+ssh`) disagree on how it is fetched, so `npm ci` can fail on a build host without an SSH key. The frontend's production listing and buying flows use a hand copied ethers v5 version of the builder, which describes itself as throwaway, rather than the shared package. Nothing tests that the two produce the same order hash. See [clusters/12-marketplace-v2/03-seaport-primer-and-the-order-entity.md](clusters/12-marketplace-v2/03-seaport-primer-and-the-order-entity.md).

### About the tests themselves

The suite grew from 86 spec files and about 594 test cases to 148 spec files and about 1,280 test cases, which is genuinely good news. Three caveats keep it from being the safety net it looks like. Nothing runs it automatically: neither CodeBuild nor the husky hooks call Jest, and `test/jest-e2e.json` has no `moduleNameMapper`, so the e2e suite cannot resolve the `@components` style imports. Some tests do not assert what their titles claim. The "ON CONFLICT DO NOTHING" tests never check that `orIgnore` was called. The market data "no network" test spies on `fetch` while the code uses axios. The health controller spec checks only `AccessTokenGuard`, so removing `AdminTokenGuard` would not fail it. And one web3 auth test is titled "throws" but asserts that the call does not throw. Finally, the poller integration spec uses fakes that ignore SQL, so it cannot prove atomicity, column quoting or conflict handling. Note 12 in cluster 12 covers all of this.

### What this update adds to the pattern

The closing lesson above was that a large codebase's real signature is inconsistency with itself. Marketplace v2 adds a second lesson, about the boundary between the backend's beliefs and the chain's truth. Nearly every serious finding in this section is a place where Postgres says one thing and the blockchain can say another: a "cancelled" order that is still fillable, a cursor that moved backwards, a sale a re org erased, a counter bump that was only logged. When you review code that mirrors on chain state, ask of every status column: what on chain event makes this true, what makes it false again, and what happens if the backend misses that event or sees it twice.
