# 02. PostgreSQL and Relational Concepts, From the Slides

The `slides` folder contains one deck, `PostgreSQL Introduction.pdf`, from the same TechZeen course the MongoDB sibling project's lecture deck comes from. It is short, eight slides, four topics with a title slide and a content slide each. This note walks through every slide's actual content and ties each point back to the real code in this repo, the same way the MongoDB project's lecture note ties embedding and referencing back to its six feature modules.

## What is PostgreSQL

The deck's own definition, word for word: "PostgreSQL is a powerful, open source relational database system. It stores data in rows and tables using SQL (Structured Query Language). It's known for stability, performance, and data integrity."

This is the core conceptual difference from the MongoDB sibling project worth sitting with before anything else. MongoDB is a document database, every record is a flexible, self contained JSON like document, stored inside a collection, and a single document can nest arbitrarily deep data inside itself. PostgreSQL is a relational database, every record is a row, every row lives inside a table with a fixed set of named, typed columns, and relationships between different kinds of data are expressed by having one table's row point at another table's row through a shared key value, rather than by nesting one document inside another. You can see this concretely in this repo, `employees.entity.ts` defines a fixed shape, `id`, `name`, `position`, `department`, every single `Employee` row has exactly those four columns, no more, no less, there is no equivalent in this codebase of Mongoose's flexible embedded subdocuments from the sibling project.

## Why use PostgreSQL

The deck lists four reasons: "It's free and open source. Supports complex queries, joins, transactions, indexing. Great choice for scalable and secure apps. Widely used in startups to enterprise level apps."

The one worth calling out specifically in the context of this repo's actual code is joins, and transactions. This repo's `employees.service.ts` does not use a SQL join anywhere (there is only one entity being queried, `Employee`), but it does use TypeORM's `createQueryBuilder()` inside its `search()` method, which is the tool you would reach for the moment a real query needed a join, a feature none of this repo's actual queries currently exercise since there is no second related entity to join against. Transactions, likewise, are a concept the slide names but that nowhere appears in this codebase's actual TypeORM calls, every write in `employees.service.ts` (`create`, `update`, `delete`) is a single independent statement, not multiple statements wrapped together so they either all succeed or all roll back together.

## Power of PostgreSQL, SQL plus NoSQL hybrid

This slide is the most conceptually interesting one for a reader coming from the MongoDB sibling project. The deck's own words: "It's relational like MySQL (tables, schemas, joins). But also supports NoSQL features like JSON and JSONB columns, full text search, arrays and custom data types. So, it gives you the power of both SQL and NoSQL in one system."

This is a genuinely accurate description of real PostgreSQL, it is one of the reasons PostgreSQL is often chosen over a strictly relational database like plain MySQL, you get the guarantees and structure of tables and foreign keys, while still being able to store a loosely structured JSON blob in a single column (a `jsonb` column) when a piece of data genuinely does not fit a fixed schema well. It is worth being precise about this repo's own code here though, since it would be easy to overstate: nothing in this project's actual entities uses a `jsonb` column, an array column, or full text search, both `Employee` and `User` are defined with entirely plain, fixed columns (`@Column()` with no special type given, which TypeORM will map to an ordinary `varchar` or similar column based on each property's TypeScript type). The slide describes a real and important capability of PostgreSQL as a database engine, but this particular teaching repo only ever exercises the plain relational half of that story, not the JSON or NoSQL flavored half.

## What is TypeORM

The deck's own words: "TypeORM is an Object Relational Mapper for TypeScript. It connects your NestJS app with PostgreSQL using OOP style code. You define tables as classes using decorators like @Entity, @Column, etc. It makes database queries easier, readable, and type safe."

This sentence is the exact bridge into every entity and service file in this repo. An ORM, object relational mapper, is a library that lets you interact with a relational database by writing and manipulating ordinary classes and objects in your programming language, rather than writing raw SQL strings by hand. TypeORM specifically is the ORM this project uses, wired into NestJS through the separate `@nestjs/typeorm` integration package, and every one of its four bullet points maps directly onto something you can point at in this repo: "define tables as classes using decorators" is exactly `@Entity()` and `@Column()` in `employees.entity.ts` and `user.entity.ts`, covered fully in [03-typeorm-entities-vs-mongoose-schemas.md](03-typeorm-entities-vs-mongoose-schemas.md), and "makes database queries easier, readable, and type safe" is exactly what `Repository<Employee>` gives `employees.service.ts`, methods like `.find()`, `.findOneBy({ id })`, and `.save()` that return properly typed `Employee` objects rather than raw untyped rows, covered fully in [04-employees-module-repository-and-service.md](04-employees-module-repository-and-service.md).

## How this compares to what the MongoDB sibling project taught

If you already read the MongoDB project's own lecture note, the useful mental model to carry forward is this: both projects solve the exact same underlying problem, letting a NestJS application read and write persistent data through a strongly typed, decorator based class, without hand writing raw database queries everywhere. `@nestjs/mongoose`'s `@Schema()`/`@Prop()` pair and `@nestjs/typeorm`'s `@Entity()`/`@Column()` pair are doing conceptually the same job, describing the shape of one unit of stored data as a decorated TypeScript class. Where they genuinely diverge is in what that unit of data means underneath: a Mongoose schema describes one flexible document that can embed other data directly inside it or reference other documents by an `ObjectId`, while a TypeORM entity describes one rigid table row whose relationships to other rows (not demonstrated anywhere in this particular repo, since it only has two unrelated entities) would be expressed with TypeORM's own relationship decorators like `@OneToMany()` or `@ManyToOne()`, which map onto real SQL foreign keys rather than an embedded document or an array of ids.
